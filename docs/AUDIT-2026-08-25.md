# Audit général — tssr.miyukini.com

**25 août 2026** · Grille d'audit MIP, tous référentiels : optimisation, UI/UX,
onboarding, comparaison concurrentielle, cybersécurité, pentest, RGPD et
informations légales.

> **Méthode.** Revue du code (`server/`, `client/`, 37 tables SQLite), mesures en
> production sur `https://tssr.miyukini.com`, lecture seule de la base locale.
> Les tests offensifs sont **non destructifs** : aucune écriture, aucun
> contournement d'authentification, aucune charge répétée au-delà de quelques
> requêtes.
>
> Chaque constat porte sa preuve — commande reproductible ou `fichier:ligne`.

---

## 0. Verdict

**La sécurité de ce site est nettement au-dessus de la moyenne.** CSP stricte
réellement active, bcrypt, régénération de session à l'élévation de privilège,
neuf limiteurs de débit, requêtes paramétrées partout, uploads assainis,
échappement avant surlignage. Rien de ce que j'ai tenté n'a produit de fuite.

**Le problème n'est pas là. Il est dans la visibilité.** Le site publie 183
pages de cours de qualité, et il est structurellement incapable d'être indexé
correctement : chaque page existe à deux URL, une seule porte des métadonnées,
et c'est **l'autre** que tous les liens du site utilisent.

| Axe | Note | Ce qui la fixe |
| --- | :-: | --- |
| Cybersécurité | **A−** | CSP, bcrypt, sessions, débit : du travail sérieux |
| Pentest | **A−** | Aucune fuite trouvée ; surface XSS limitée à l'admin |
| Optimisation technique | **B+** | 72 chunks, brotli, cache immuable — bien fait |
| **Référencement** | **D** | Double URL, aucun canonical, `og:url` = example.com, pas de sitemap |
| UI / UX & accessibilité | **B−** | Structure sémantique présente, mais ni lien d'évitement ni `prefers-reduced-motion` |
| Onboarding | **B** | Hub clair, 183 pages ; la double URL brouille les favoris |
| Concurrentiel | **A−** | Les outils interactifs n'ont pas d'équivalent |
| RGPD / légal | **D** | **Zéro page légale** sur 183 ; risque latent, pas encore réalisé |

**Une seule correction change la trajectoire du site** : unifier les URL et
définir `PUBLIC_BASE_URL`. Une demi-journée.

## 2. Optimisation et référencement

La performance technique est bonne. Le référencement ne l'est pas — et c'est
là que se joue l'utilité du site.

### 2.1 Constat O-1 — Chaque page existe à deux URL, une seule est référençable *(Élevé)*

`server/lib/seo.ts:33` :

```js
} else if ((m = path.match(/^\/([^/]+)$/))) {
  const p = db.select().from(pages).where(...).get();
  if (p) return { ...base, title: `${p.title} — ${brand}`, description: … };
}
```

Cette expression n'accepte **qu'une seule section**. Résultat mesuré :

```
GET /linux-bases        →  <title>Linux : les bases (Debian) — TSSR Cyber 26/02</title>
GET /pages/linux-bases  →  <title>TSSR Cyber 26/02</title>
```

Les deux URL renvoient **le même contenu, en HTTP 200**. La première a un
titre, une description, des balises Open Graph. La seconde n'a rien.

Or c'est la seconde qui est utilisée partout. Le menu du site le montre :

| Entrée du menu | URL | SEO |
| --- | --- | :-: |
| Accueil | `/` | ✅ |
| Glossaire | `/glossaire` | ✅ |
| Stages | `/stages` | ✅ |
| **Cours** | `/pages/cours` | ❌ |
| **Exercices** | `/pages/exercices` | ❌ |
| **Procédures** | `/pages/procedures` | ❌ |
| **Outils** | `/pages/scripts` | ❌ |

Les quatre rubriques de contenu — celles qui portent les 183 pages — sont du
mauvais côté. Tous les liens internes entre cours (`/pages/linux-reseau`,
`/pages/repertoire-commandes`…) le sont aussi.

**Trois dommages cumulés :**

1. **Contenu dupliqué** sur l'intégralité du site, sans arbitrage.
2. **Aucun titre distinct** dans les résultats de recherche : 183 pages
   remonteraient toutes sous « TSSR Cyber 26/02 ».
3. **Aucun extrait** : sans `<meta name="description">`, le moteur invente le
   résumé — ou n'indexe pas.

> **Remédiation.** Choisir une forme canonique. Le plus simple sans casser les
> liens existants : élargir la regex et rediriger en 301.
> ```js
> } else if ((m = path.match(/^\/(?:pages\/)?([^/]+)$/))) {
> ```
> Puis, côté serveur, `301` de `/pages/:slug` vers `/:slug` (ou l'inverse), et
> mise à jour du menu.

### 2.2 Constat O-2 — `PUBLIC_BASE_URL` n'est pas défini en production *(Élevé)*

`env.ts:68` :

```js
export const PUBLIC_BASE_URL = process.env.PUBLIC_BASE_URL || 'https://example.com';
```

La valeur par défaut est en production. Mesuré :

```
GET /            →  <meta property="og:url" content="https://example.com/"/>
GET /linux-bases →  <meta property="og:url" content="https://example.com/pages/linux-bases"/>
```

**Chaque page du site déclare appartenir à `example.com`.** Conséquences
directes : un partage sur un réseau social ou une messagerie affiche une carte
pointant vers un domaine tiers ; `abs()` (`seo.ts:10`) préfixe aussi les images
Open Graph, donc `og:image` est également cassé.

C'est le défaut le moins coûteux à corriger de tout cet audit — **une variable
d'environnement dans `ecosystem.config.cjs`** — et l'un des plus dommageables.

### 2.3 Constat O-3 — Toute URL renvoie 200 *(Élevé)*

```
GET /pages/xyz-inexistant-42  →  HTTP 200
GET /route-totalement-fausse  →  HTTP 200
```

Le repli SPA sert `index.html` avec un code 200 quel que soit le chemin. Un
moteur de recherche considère donc que **toutes** les URL existent : il indexe
des pages vides, dépense son budget d'exploration sur du néant, et perd
confiance dans le site.

> **Remédiation.** Avant le repli SPA, résoudre le slug en base ; si aucune
> page ne correspond et que la route n'est pas connue du routeur, répondre
> **404** avec la même coquille HTML. Le rendu reste identique pour l'humain,
> le statut devient juste pour la machine.

### 2.4 Constat O-4 — Pas de sitemap, et robots.txt n'en annonce aucun *(Moyen)*

```
GET /sitemap.xml  →  HTTP 200, Content-Type: text/html  (c'est le SPA)
robots.txt        →  aucune directive « Sitemap: »
```

Il n'y a **pas de sitemap**. Pour un site de 183 pages dont la navigation passe
par des hubs, c'est le moyen le plus efficace de garantir l'exploration
complète — et il est absent.

Le `robots.txt` servi est celui de Cloudflare (*Content Signals*). Il autorise
la recherche et **bloque explicitement** `GPTBot`, `ClaudeBot`, `CCBot`,
`Google-Extended`, `Bytespider`, `Amazonbot`, `Applebot-Extended`,
`meta-externalagent` — c'est-à-dire l'entraînement des modèles.

Ce choix est parfaitement légitime, mais il mérite d'être **conscient** : il
n'a probablement pas été fait dans l'application. À vérifier dans le tableau de
bord Cloudflare.

### 2.5 Constat O-5 — Aucune balise canonique *(Moyen)*

`metaTags()` (`seo.ts:41-58`) émet `<title>`, description, Open Graph et
Twitter Card. **Il n'émet jamais `<link rel="canonical">`** — vérifié en
production : `grep -c 'rel="canonical"'` → **0**.

Sans canonique, rien ne tranche entre `/linux-bases` et `/pages/linux-bases`
(O-1), ni entre une URL avec et sans paramètres. C'est une ligne à ajouter :

```js
`<link rel="canonical" href="${url}"/>`,
```

### 2.6 Performance — correcte, avec une réserve

| Mesure | Valeur | Appréciation |
| --- | ---: | --- |
| HTML de la page d'accueil | 12,3 Ko / 0,19 s | Très bien |
| Bundle d'entrée | 407 Ko → **127 Ko brotli** | Acceptable, à surveiller |
| CSS | 78 Ko → **15,5 Ko brotli** | Très bien |
| Chunks JS produits | **72** | Le découpage fonctionne |
| Cache des assets | `immutable`, 30 j | Optimal |

La seule réserve porte sur l'entrée : 407 Ko avant compression pour un site
dont la majorité des visites est une lecture de cours. Router, React Query et
la coquille d'administration sont probablement dans ce bundle. Un découpage
`admin` / `public` économiserait sur la première visite — c'est une
optimisation de confort, pas une urgence.

## 3. UI/UX et accessibilité — ISO 9241-110, WCAG 2.2

> **Précision de méthode.** Le HTML servi est une coquille SPA : y chercher des
> `<h1>` ne prouve rien. Les chiffres ci-dessous viennent du **code React**,
> qui est ce qui compose réellement le DOM.

| Élément | Occurrences dans `client/src/` | Lecture |
| --- | ---: | --- |
| `<h1>` | **73** | Hiérarchie de titres réellement travaillée |
| `<main>` | 3 | Présent, mais sur 3 gabarits seulement |
| `<nav>` | 2 | idem |
| `<footer>` | 2 | idem |
| `aria-label` | 26 | Étiquetage explicite là où il manque |
| `aria-current` | 2 | Élément actif signalé — bon réflexe |
| `:focus-visible` | 2 | Focus stylé, au moins partiellement |
| `prefers-color-scheme` | 1 | Thème clair/sombre géré |
| **Lien d'évitement** | **0** | ❌ |
| **`prefers-reduced-motion`** | **0** | ❌ |
| **`<noscript>`** | **0** | ❌ |

### 3.1 Constat U-1 — Aucun lien d'évitement *(Moyen)*

WCAG 2.2 **2.4.1 (Contourner des blocs)**, niveau A. Sur un site dont chaque
page commence par un en-tête et un menu, un utilisateur au clavier ou au
lecteur d'écran doit traverser toute la navigation à chaque page — pour 183
pages, c'est disqualifiant.

> **Remédiation.** Un lien en tout premier dans le DOM, visible au focus :
> ```html
> <a href="#contenu" class="skip">Aller au contenu</a>
> ```
> plus `id="contenu"` sur le `<main>`. Une dizaine de lignes de CSS.

### 3.2 Constat U-2 — Repères sémantiques incomplets *(Faible)*

3 `<main>` et 2 `<nav>` pour l'ensemble de l'application : les gabarits
principaux sont couverts, mais il faut vérifier que **chaque** vue publique en
hérite. Sans `<main>`, la navigation par régions d'un lecteur d'écran n'a pas
de point d'entrée.

### 3.3 Constat U-3 — Animations non désactivables *(Faible)*

Aucune règle `@media (prefers-reduced-motion: reduce)`. WCAG **2.3.3** (AAA)
et, plus concrètement, un vrai inconfort pour les personnes sujettes au mal des
transports vestibulaire. Le site comporte des outils interactifs animés
(schémas, wizards) — c'est exactement le cas d'usage visé par ce critère.

### 3.4 Constat U-4 — Sans JavaScript, page blanche *(Faible)*

Aucun `<noscript>`. Le site étant intégralement rendu côté client, un
navigateur avec JS désactivé — ou un chargement de bundle qui échoue — affiche
une page vide sans explication. Une ligne suffit à transformer un mystère en
message.

## 4. Onboarding

### 4.1 Ce qui va

183 pages **toutes publiées**, organisées en quatre hubs (Cours, Exercices,
Procédures, Outils) plus Glossaire et Stages. Le hub des procédures est
catégorisé et filtrable. Les TP renvoient vers les cours et réciproquement.
Pour un site de révision, l'architecture d'information est claire.

### 4.2 Constat N-1 — La double URL brouille les repères de l'apprenant *(Moyen)*

Conséquence humaine de O-1, distincte du dommage SEO :

- un étudiant qui met `/pages/linux-bases` en favori et un autre qui met
  `/linux-bases` ont **deux entrées différentes pour la même page** ;
- l'onglet du navigateur affiche « TSSR Cyber 26/02 » sur la variante
  `/pages/…` — donc **le même titre pour tous les onglets ouverts**. Avec
  quinze onglets de révision, aucun n'est identifiable ;
- une recherche interne ou un partage entre camarades produit l'une ou l'autre
  forme, sans cohérence.

Le titre d'onglet est le point le plus tangible : il se corrige avec O-1.

### 4.3 Constat N-2 — Une erreur d'URL ne dit rien *(Faible)*

Une adresse mal recopiée renvoie 200 et affiche la coquille. L'étudiant ne sait
pas s'il s'est trompé, si la page a été supprimée, ou si le site est en panne.
Un vrai 404 avec un lien vers le hub le plus proche résout la question.

## 5. Comparaison concurrentielle

| Solution | Ce qu'elle fait mieux | Ce que TSSR-miyukini fait mieux |
| --- | --- | --- |
| **Moodle / LMS** | Comptes, progression, quiz notés, devoirs, cohortes | Pas de lourdeur d'installation ; contenu bien plus lisible ; les outils interactifs sont **hors de portée** d'un LMS |
| **GitBook / Docusaurus / MkDocs** | SEO impeccable par défaut, versionnement Git, recherche intégrée | **L'interactivité** : un site statique ne peut pas héberger un atelier réseau ni un simulateur |
| **it-connect.fr, OpenClassrooms** | Audience, référencement, notoriété | Contenu **aligné sur le référentiel TSSR** et sur les TP réellement distribués en formation |
| **Cisco NetAcad / Packet Tracer** | Simulation réseau de référence | Accessible dans le navigateur, sans compte ni installation ; couvre aussi Windows, AD et Linux |
| **Notion / Obsidian publiés** | Rapidité de rédaction | Vraie mise en page, vrais outils, contrôle du domaine |

### 5.1 L'atout différenciant

Ce site a quelque chose que **rien de ce qui précède n'a** : des outils
pédagogiques interactifs écrits sur mesure pour le programme.
`NetworkWorkshop` (169 Ko), `WindowsSim` (59 Ko), `AgdlpBuilder` (41 Ko), le
configurateur d'adressage Debian, le répertoire de commandes interrogeable en
français. Ce ne sont pas des illustrations : ce sont des simulateurs où
l'erreur est expliquée.

C'est le genre d'actif qui justifierait une audience bien plus large que celle
d'une promotion.

### 5.2 Ce qui l'en empêche

Exactement les constats du § 2. Un site invisible pour les moteurs a l'audience
de sa liste de diffusion. **La faiblesse concurrentielle de ce site n'est pas
son contenu, c'est son indexation** — et c'est ce qui rend O-1 et O-2
prioritaires malgré leur apparence anodine.

### 5.3 Ce qui manquerait pour rivaliser avec un LMS

Les tables existent (`customers`, `forum_topics`, `comments`,
`form_submissions`) mais sont **toutes à zéro**. Il n'y a donc, aujourd'hui, ni
compte apprenant, ni suivi de progression, ni score conservé. C'est un choix
défendable — et c'est aussi ce qui maintient le risque RGPD à zéro (§ 8).

## 6. Cybersécurité — ISO/IEC 27001, CISSP, CISA

Le § 1 recense ce qui est en place, et c'est l'essentiel. Ne restent que des
points secondaires.

### 6.1 Constat C-1 — Le limiteur de débit est mono-processus *(Faible, mais à connaître)*

`lib/rate-limit.ts` conserve ses compteurs dans une `Map` en mémoire. Le
commentaire le dit honnêtement (« mono-instance »), et `ecosystem.config.cjs`
ne déclare pas d'`instances` — donc PM2 tourne en mode *fork*, un seul
processus : **le limiteur fonctionne aujourd'hui**.

Le risque est différé : passer PM2 en `cluster` avec 4 instances **quadruple
silencieusement toutes les limites**, sans aucun message. Un limiteur qui se
dégrade sans le dire est plus dangereux qu'un limiteur absent.

> **Remédiation.** Un commentaire dans `ecosystem.config.cjs` — « ne pas passer
> en mode cluster sans déporter le limiteur » — coûte une ligne et évite une
> régression invisible.

### 6.2 Constat C-2 — `X-Powered-By: Express` *(Faible)*

Présent en production. Divulgation de technologie sans conséquence directe,
mais gratuite à supprimer : `app.disable('x-powered-by')`.

### 6.3 Constat C-3 — Asymétrie de temps au login *(Faible — non exploitable ici)*

`routes/auth.ts:24` :

```js
if (!admin || !bcrypt.compareSync(password, admin.password_hash)) {
```

Court-circuit : si le compte n'existe pas, **bcrypt n'est jamais exécuté**. En
théorie, la réponse est ~100 ms plus rapide, ce qui permet d'énumérer les
comptes.

**Mesuré, ce n'est pas exploitable** — 4 requêtes par cas :

```
admin           : 0,686  0,474  0,444  0,471
nexistepas-zzz  : 0,663  0,730  0,942  1,077
```

Le compte inexistant est même *plus lent*. La gigue réseau et Cloudflare
dominent largement le signal. Le constat reste valable au niveau du code — la
correction est un `bcrypt.compareSync(password, HASH_FACTICE)` dans la branche
« compte absent » — mais **la cote reste faible : c'est de l'hygiène, pas une
faille**.

### 6.4 Sur l'absence de jeton CSRF

Il n'y a pas de jeton anti-CSRF. Ce n'est **pas** un défaut ici : le cookie de
session est `SameSite=Lax`, ce qui empêche le navigateur de l'envoyer sur une
requête POST inter-site, et toutes les routes d'écriture sont en POST / PUT /
DELETE. La protection est structurelle plutôt qu'explicite — c'est un choix
valable, à documenter pour que personne n'ajoute un jour une écriture en GET.

## 7. Pentest — revue offensive (CEH)

> Boîte blanche, non destructif. Aucune écriture, aucun contournement
> d'authentification, aucune charge soutenue.

### 7.1 Ce qui a été tenté — et n'a rien donné

| Vecteur | Résultat | Détail |
| --- | :-: | --- |
| Fuite de fichiers sensibles | **Aucune** | `/cms.sqlite`, `/.env`, `/ecosystem.config.cjs`, `/uploads/` renvoient tous **la coquille SPA** (`text/html`, ~2,6 Ko), pas les fichiers. Vérifié sur le corps de la réponse, pas seulement sur le code |
| Accès admin non authentifié | **401** | `/api/admin/pages` et `/api/auth/me` refusent proprement |
| Injection SQL | **Aucun vecteur** | Drizzle paramétré ; seule interpolation sur nom de table issu de `sqlite_master` |
| Traversée par nom de fichier (upload) | **Impossible** | `media.ts:39` réduit à `[a-zA-Z0-9_-]`, préfixe et impose l'extension |
| XSS via recherche / glossaire | **Bloqué** | `escHtml()` **avant** insertion des `<mark>` — l'ordre correct |
| XSS via extrait de recherche | **Bloqué** | `search.ts:92` : marqueurs `char(2)/char(3)`, échappement, puis substitution |
| Énumération de comptes par le temps | **Non mesurable** | § 6.3 |
| CSRF | **Mitigé** | `SameSite=Lax` sur toutes les écritures POST |

### 7.2 Constat T-1 — La surface XSS existe, mais elle est du côté admin *(Faible)*

11 emplacements utilisent `dangerouslySetInnerHTML` côté client :
`RichContent.tsx:153`, `PageBuilder.tsx:63`, `NoteEmbed.tsx:12`,
`Glossary.tsx:146`, `ProductView.tsx:38`, `QuoteFormView.tsx:52`,
`WizardPager.tsx:45`, et les quatre surlignages déjà traités.

Tous rendent du **contenu rédigé depuis l'administration** : blocs de page,
descriptions de produit, définitions de glossaire, introductions de
formulaire. C'est le fonctionnement voulu d'un CMS — la mise en page riche
suppose du HTML.

**Aucun contenu de visiteur n'atteint ces points** : les commentaires, sujets
de forum et soumissions de formulaire ne passent par aucun de ces sinks.

La conséquence est donc bornée : un attaquant qui parviendrait à injecter du
HTML y serait déjà administrateur — auquel cas le XSS est le moindre de ses
pouvoirs. **La CSP `script-src 'self'` bloque de surcroît tout script inline**,
ce qui neutralise la charge la plus courante.

> C'est le bon niveau de rigueur pour ce site. À réévaluer **le jour où les
> commentaires ou le forum s'ouvrent** : il faudra alors assainir côté serveur
> avant stockage, et non se reposer sur la CSP.

### 7.3 Constat T-2 — Le verrou de site privé est configuré mais inactif *(À confirmer)*

La base contient `site_gate_hash` (empreinte bcrypt), et `routes/settings.ts:263`
expose `/api/site-access` avec son propre limiteur. Le mécanisme est complet.

Mais le contenu est servi **sans aucune authentification** :

```
GET /api/public/pages/linux-bases  →  200, contenu intégral
```

Le verrou existe donc sans être armé. Si le site est **volontairement public**,
tout va bien et il n'y a rien à faire. Si l'intention était de le restreindre à
la promotion, **il n'est pas restreint** — et les 183 pages, y compris les
corrigés de TP, sont lisibles par quiconque connaît l'adresse.

C'est le seul point de cet audit qui appelle une décision plutôt qu'un correctif.

## 8. RGPD et informations légales

### 8.1 Constat R-1 — Aucune page légale sur 183 *(Élevé sur le plan légal)*

Requête sur la base, recherche des slugs et titres contenant *legal, mention,
cgv, cgu, confidential, privacy, cookie, rgpd, données* :

```
total pages : 183   publiées : 183
pages légales trouvées : AUCUNE
```

Il manque, pour un site accessible publiquement :

| Document | Fondement | Statut |
| --- | --- | :-: |
| **Mentions légales** | LCEN art. 6-III — éditeur, directeur de publication, hébergeur | ❌ |
| **Politique de confidentialité** | RGPD art. 13 — finalités, base légale, durées, droits | ❌ |
| **Information cookies** | Art. 82 loi Informatique et Libertés | ❌ (voir 8.3) |
| **CGV** | Obligatoire dès la première vente | ❌ — **et Stripe est branché** |

La LCEN impose les mentions légales même à un site non marchand édité par un
particulier — avec, pour un éditeur non professionnel, la faculté de ne
publier que l'hébergeur, à condition d'avoir communiqué son identité à celui-ci.

### 8.2 Constat R-2 — Le risque est latent, pas réalisé *(Moyen)*

C'est la nuance qui change la priorité. Aujourd'hui :

```
customers 0 · orders 0 · comments 0 · forum_topics 0
form_submissions 0 · quote_submissions 0
admins 2 · sessions 17
```

**Le site ne traite aucune donnée personnelle de tiers.** Il n'y a donc, en
pratique, ni registre à tenir, ni droit d'accès à honorer, ni notification à
prévoir.

Mais les fonctions sont **actives et atteignables** : inscription client,
commentaires, forum, formulaires, devis, paiement Stripe. La première
inscription fait basculer le site dans le régime complet du RGPD —
**instantanément, et sans que rien ne le signale**.

> **Remédiation proportionnée.** Deux options, l'une ou l'autre :
> 1. **Fermer ce qui n'est pas utilisé** (`requireFeature` existe déjà :
>    `comments.ts:54`, `forms.ts:129`, `forum.ts:102`). Le risque tombe à zéro
>    et il n'y a rien d'autre à écrire.
> 2. **Publier la politique de confidentialité maintenant**, tant qu'elle peut
>    être rédigée à froid plutôt que dans l'urgence.

### 8.3 Cookies — conforme, et c'est notable *(Favorable)*

Aucun script tiers n'est chargé (la CSP `script-src 'self'` l'interdirait de
toute façon), aucune mesure d'audience n'a été détectée, les polices sont
auto-hébergées.

Le seul cookie est celui de session : `httpOnly`, `secure`, `SameSite=Lax`,
8 heures. Il est **strictement nécessaire au service** → dispensé de
consentement au sens de l'article 82. **Aucune bannière n'est requise**, et
c'est la bonne façon de ne pas en avoir besoin.

### 8.4 Constat R-3 — Transfert hors UE non documenté *(Faible)*

Le site passe par un tunnel Cloudflare (`Server: cloudflare`, `CF-RAY: …-CDG`).
Le nœud est parisien, mais Cloudflare est un sous-traitant états-unien : dès
qu'il y aura des données personnelles, il faudra le mentionner dans la
politique de confidentialité et s'appuyer sur son DPA. Sans données, la
question ne se pose pas encore.

### 8.5 Constat R-4 — Pas de conservation ni de purge *(Faible)*

Aucun mécanisme de durée de conservation n'existe pour les commandes, les
soumissions de formulaire ou les sessions. Point sans objet tant que les tables
sont vides — à traiter en même temps que R-2 option 2.

## 11. Limites de cet audit

- **Aucune mesure de performance réelle** : pas de Lighthouse, pas de Core Web
  Vitals, pas de test sur réseau mobile. Les chiffres sont des poids de
  transfert, pas des temps de rendu perçus.
- **Accessibilité non testée avec un lecteur d'écran.** Les compteurs de code
  disent ce qui existe, pas si l'expérience est utilisable. Un passage NVDA sur
  trois pages types dirait bien plus.
- **Les 183 pages n'ont pas été relues.** Ni exactitude pédagogique, ni liens
  morts internes, ni cohérence entre cours et TP.
- **Aucun test d'authentification poussé** : pas de tentative de contournement
  de session, pas d'analyse de l'entropie du cookie, pas de test de fixation
  au-delà de la lecture du code.
- **Le limiteur de débit n'a pas été éprouvé** : le vérifier suppose de le
  saturer, ce qui revient à se couper l'accès. Sa correction est admise sur
  lecture.
- **Le tableau de bord Cloudflare n'a pas été consulté** — WAF, règles de
  cache, `robots.txt` géré : plusieurs comportements observés viennent de là et
  non de l'application.
